# Wave 10, DM — the demo fixture and the `Stop`-hook recipe: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to
> implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking. **The wave is the dispatch
> unit, not the task:** one implementer per lettered wave, with every task inside it keeping its own
> failing test, verification and commit. Both waves land in one pull request into `dev`, with one
> final review (the umbrella's "Execution contract", item 4). This plan cites that section by path and
> does not copy it.

**Goal:** a deterministic demo that shows what stayfixed counts, built from scratch by one script
that needs no model call, and a `Stop`-hook recipe a user installs to run `stayfixed prove` before
the agent may finish. The owner records a demo of about 90 seconds from the script on the `v0.7.0`
candidate. The script also runs as a CI job, so a broken story turns that job red.

**Architecture:** two waves, A and B, run one after the other in one worktree on branch
`wp/demo-fixture`. Wave A writes the script, its fixture repository and acts 1 to 6. Wave B writes the
recipe with its unit tests, act 7, which drives the recipe, and the CI job. Nothing under `src` changes.
The script and the recipe are Python 3.11 standard library, run with `python3 -I`, and live under
`examples/`, which ships in no plugin tree and no wheel.

**Tech Stack:** Python ≥ 3.11 standard library; `uv`, pytest (`-n auto`), ruff, mypy, the mutation
oracle (`scripts/mutation_oracle.py`, entries routed by `GROUP_OF`), towncrier fragments in
`changelog.d/`, GitHub Actions (`.github/workflows/ci.yml`).

**Spec:** the wave-10 umbrella plan, `docs/plans/2026-10-28-wave-10-umbrella.md`: lane DM in
"Lanes", the DM row of "Lane-plan items", the edge IS1 → DM in "Launch graph", and the `examples/` row
of "File ownership and hot spots". The private design's §15.10 decisions 3 (the recipe) and 5 (the
fixture) are carried by that row, which is restated here so the implementer needs nothing else:

> **`examples/`:** a script that builds a small repository from scratch, takes the `stayfixed`
> binary as an argument, prints `command -v` and `--version` first, and needs no model call and no
> network beyond a pinned, pre-installed pytest. Each act asserts the product's own exit code and
> its `--json` or stdout, never a line the script echoes. **1.** `prove` on a genuine run
> (`proved`, exit 0). **2.** `prove -- sh -c 'echo "42 passed"'` (`not proven`, exit 1). **3.** An
> all-skipped suite (`failed`, exit 1). **4.** A forging spelling (`refused`, exit 2). **5.** A closed
> bug whose regression fails an **enforced** gate (the gate's state set and asserted, then the
> verdict and the exit). **6.** `attach` under an isolated `HOME` over a scratch overlay holding one
> canary addressed to the project and one to another: the first arrives, the second does not, and
> `git status --porcelain` is empty before and after. **7.** The `Stop`-hook recipe: a shipped
> example hook that runs `stayfixed prove -- <tests>` and exits 2 on anything but `proved`, with a
> stated cost per turn (a turn with no edit pays the run too), driven once on a red tree (exit 2),
> once on a green one (exit 0), and once on a red tree with `stop_hook_active: true` in its input
> (exit 0). The recipe reads its stdin JSON and lets the stop through when `stop_hook_active` is
> true, so a tree the agent cannot make green costs one continuation, not an unbounded loop. Its
> sentence: the adversary is the agent's "done"; the agent in the session can edit the hook's
> settings file or weaken the tests, so the anchor is the user's own install and the harness's
> sandbox, and the recipe says so where it is shipped. **CI:** a job in `ci.yml` runs the script
> against the checkout's binary; act 6 needs `claude` on the runner, or that act is skipped and the
> skip is printed, never counted as a pass. "Under a minute" is a goal printed with the measured
> time, not an assertion.

**`Stop` semantics this plan builds on**, read on 2026-10-28 in Claude Code's hooks reference
(`https://code.claude.com/docs/en/hooks.md`, sections "Stop", "Stop input" and "Stop decision
control"; Claude Code 2.1.312 installed on the controller's machine):
- `Stop` runs when the main agent finishes responding. It does not run when the user interrupted,
  and an API error fires `StopFailure` instead.
- Its input carries `stop_hook_active`, "`true` when Claude Code is already continuing as a result
  of a stop hook", with the advice to check it "to avoid blocking on a condition that will never
  resolve". It also carries `cwd`, which follows the agent into a worktree or after a `cd`.
- Exit 2 keeps the agent working, and its stderr becomes the reason it is given. Any other non-zero
  exit is a non-blocking error: the stop goes ahead and the user sees it.
- A JSON object on stdout is read on **every** exit code, and on an exit other than 0 or 2 its fields
  alone decide. So the recipe prints nothing on stdout, ever.
- Claude Code caps stop-hook continuations at eight in a row, and the count resets each time the
  agent calls a tool. An agent that runs the tests between stops resets it, so the cap does not bound
  a recipe that blocks every stop. The `stop_hook_active` let-through does.
- A command hook's default timeout is 600 seconds. Past it, the hook ends as a non-blocking error and
  the stop goes ahead. The recipe passes `prove` a `--timeout` below that, so `prove` ends its own
  run first.

## Global constraints

- Standard library only, no new dependency. The script and the recipe never import `stayfixed`: they
  drive the binary they are given, as a user would.
- **Assert the product, never the script.** Every act's verdict comes from the product's exit code
  and from its `--json` object parsed off its stdout, or for act 6 from what the product wrote under
  the isolated `HOME`. A line the script prints is never read back.

Each line is a failure the lane could cause that no single task's tests would show, with what pins it.

1. **An act that cannot fail.** An assertion read from the script's own output, or an expectation
   copied from what the product printed, passes whatever the product says. Pinned by Task 3, Step 3:

   under `--require-claude`, which the CI job passes. Pinned by Task 3's two runs, with and without
   `claude` on `PATH`.
3. **The recipe loops the agent.** A recipe that ignores `stop_hook_active` blocks every stop on a
   tree the agent cannot make green, and Claude Code's cap of eight resets on every tool call. Pinned

4. **The recipe speaks on stdout.** Claude Code reads a JSON object on stdout on every exit code, so
   `prove --json`'s object passed through would be read as the hook's own answer. Pinned by Task 4's
   assertion, in every case, that the recipe's stdout is empty.
5. **Act 5 spells a key #31 removed.** Pinned by Task 2, Step 0: act 5 leaves the adoption keys to
